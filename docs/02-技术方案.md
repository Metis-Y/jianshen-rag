# 02 · 技术方案

## 1. 架构

```
浏览器（Vue 3 + Vite）
  │ dev: vite proxy / 演示: FastAPI 托管 dist（同源）
  ▼
FastAPI 应用（本机运行）
  ├─ SQLite         业务数据：用户/文档/会话/消息/反馈
  ├─ ChromaDB       向量与 chunk 原文（本地目录持久化）
  ├─ 本地磁盘       原始文档 {uploads}/{userId}/{md5}/{filename}
  └─ 外部 API       硅基流动（Embedding + 对话），OpenAI 兼容
```

单进程、单机、零 Docker、零外部服务依赖（模型走 API）——对业务闭环项目，
这是**可维护性最优**的形态。

## 2. 数据流

**上传链路**（同步处理，接口内完成）：

```
POST /api/documents (multipart)
  → MD5 计算 → 命中已有 READY 文档 → 秒传返回
  → 存磁盘 → SQLite 记 document(status=PENDING)
  → LangChain loader 解析失败 → status=FAILED + 失败原因（结束）
  → splitter 切分 → 逐块 embedding（批量）
  → 写入 Chroma collection（metadata 带 doc_id/title/章节/序号）
  → status=READY，返回 chunk 数
```

**问答链路**：

```
POST /api/chat（SSE）
  → 问题 embedding → Chroma 相似检索 topK=5（按 userId 过滤）
  → Prompt 组装（引用约束：只基于资料、不足就说没有、标注 [n]）
  → LLM 流式生成 → SSE: citations → message(delta)... → done
  → 完整回答与引用落库（SQLite message）
```

## 3. 选型决策

### 3.1 后端：FastAPI 而不是 Django/Flask

- 原生 async + StreamingResponse（SSE 顺手），自动 OpenAPI 文档
- 简历上「FastAPI」在 AI 应用岗是高频词
- Django 过重（闭环业务用不到 admin/ORM 全家桶），Flask 无 async 原生能力

### 3.2 数据库：SQLite 而不是 MySQL

- 闭环业务的数据量：几个用户、几百条消息——SQLite 绰绰有余
- **换 MySQL 是改一行连接串的事**（SQLAlchemy 隔离了方言），面试这样答即是懂取舍
- 零运维：clone 仓库就能跑，验证闭环与演示都不依赖环境

### 3.3 向量库：ChromaDB（本地模式）而不是 ES / Milvus

- **Python 原生**：`pip install chromadb` + 两行初始化，不需要 Docker 与服务端进程
- 数据量（几百 chunk）下性能无差异；ES 需要 JVM 部署、内存不小
- 之前设计 Java 版 RAG 时验证过：ES 在虚拟机上要近 1G 内存；Chroma 本地百 MB 级
- 换向量库同样走抽象：检索函数只有一处，二期切 Milvus/ES 不伤业务代码

### 3.4 文档处理：LangChain 还是手写

| 环节 | 选择 | 理由 |
| --- | --- | --- |
| 文档加载（PDF/Word/MD） | LangChain loaders | 各格式坑多（编码/加密/分页），用社区成熟实现 |
| 切分 | LangChain `RecursiveCharacterTextSplitter` | 参数化（chunk 大小/重叠），符合"不深"原则 |
| Embedding / LLM 调用 | OpenAI SDK 指向硅基流动 | 协议统一，不用额外封装 |
| 检索查询 + Prompt 组装 | **自己写** | 业务核心，必须逐行可控 |

### 3.5 流式：SSE

LLM 输出是单向流，SSE 是标准解；FastAPI `StreamingResponse` 天然支持。
不使用 WebSocket：双向能力用不上，客户端的重连/心跳是纯负担。

**过 nginx 的坑**：nginx 默认缓冲响应，SSE 会被憋住一起发，表现为“逐字”变“整段”。
nginx 配置需 `proxy_buffering off;`（响应头 `X-Accel-Buffering: no` 亦可）。

### 3.6 前端：Vue 3 + Vite + nginx

- 与 ShowTicket / interview-rag 同套技术栈（Vue3/Vite/Axios/nginx 反代），学习与维护成本趋零
- 端口：FastAPI 8000，nginx 8090，`/api` 反代；dev 模式用 Vite proxy
- 三页：登录、文档管理（上传/列表/状态）、问答（SSE 逐字 + 引用卡片）

### 3.6 认证：JWT（单用户体系，无 RBAC）

- 注册/登录签发 JWT，业务接口依赖项里校验——与你 ShowTicket 的手写拦截器形成
  「两个语言、两种认证实现」的对比素材
- pyjwt 三行代码量，与控制闭环的复杂度匹配

## 4. 关键配置（全走环境变量/配置文件）

| 键 | 默认 | 说明 |
| --- | --- | --- |
| SILICONFLOW_API_KEY | 必填 | 硅基流动 key |
| EMBEDDING_MODEL | BAAI/bge-m3 | 1024 维 |
| CHAT_MODEL | deepseek-ai/DeepSeek-V3 | 可换 Qwen |
| CHUNK_SIZE / OVERLAP | 500 / 80 | 字符数 |
| TOPK | 5 | 检索块数 |
| MAX_UPLOAD_MB | 20 | 上传上限 |
| CHROMA_DB_PATH | ./chroma_db | 本地持久化路径 |
| UPLOAD_DIR | ./data/uploads | 原件目录 |
