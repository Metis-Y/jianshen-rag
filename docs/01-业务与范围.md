# 01 · 业务与范围

## 1. 一句话定位

把训练计划、营养知识等资料，和个人每天的训练、体重、饮食记录放进同一个系统，
用自然语言既能问"怎么做"（带出处），也能问"我最近怎么样"（带自己的数据）。

## 2. 目标用户

有健身习惯、或正在开始健身、想通过记录看到效果的人。产品自身为多用户设计
（注册独立账号、数据按用户隔离），不依赖学校或企业场景。

## 3. 三条业务主线

### 3.1 计划主线（RAG）

- 上传训练计划、动作原理等文档（PDF/Word/MD）
- 问"深蹲日怎么安排""这几个动作怎么排序" → 回答引用文档原文
- 状态反馈：解析处理中 → 就绪 / 失败（给出原因，如扫描件）

### 3.2 效果主线（结构化数据）

- 每日记录：训练日志（动作、重量、组数、次数）+ 体重/体脂
- 问"这周训练容量趋势""体重怎么变" → 后端聚合 SQLite 数据 → LLM 生成**文字趋势总结**
- （一期用文字呈现，图表留二期；不是缺失，是画线）

### 3.3 饮食主线（RAG + 记录）

- 上传营养资料；每日记录"吃了什么"（可附忌口标签）
- 问"减脂期晚餐怎么吃" → 引用营养资料，结合我记录过的忌口给出建议

## 4. 五条验收标准（闭环定义）

| # | 验收动作 | 通过标准 |
| --- | --- | --- |
| 1 | 上传《腿部训练计划》后问"深蹲日怎么安排" | 回答引用该文档，出处可见 |
| 2 | 记录 3 天训练+体重后问"这几天的容量和体重趋势" | 回答引用我的真实数据，无编造 |
| 3 | 删除某份营养文档后问相关内容 | "知识库中没有相关内容" |
| 4 | 记录忌口"不喝牛奶"后问"减脂早餐吃什么" | 回答避开牛奶，且引用营养资料 |
| 5 | 二轮问答后回看 + 点赞/踩 | 历史完整、统计正确 |

## 5. 数据记录的粒度决策（与你的记录成本强相关）

训练日志采用**结构化轻量 JSON**存储（单次记录 = 动作列表[动作/重量/组数/次数]），
而非零散表——既能算"总容量 = Σ重量×次数"，录入成本又可控。

一期只跟踪两个核心指标，不贪多：

| 指标 | 计算 | 用途 |
| --- | --- | --- |
| 训练容量 | Σ(重量 × 次数 × 组数) | 训练趋势、加重建议 |
| 体重 | 直接记录 | 减脂/增重趋势 |

体脂、围度等指标字段预留，但不做统计（画线）。

## 6. 功能边界（不做 = 画线）

| 不做 | 理由 |
| --- | --- |
| 动作视觉纠错（视频/图片） | 需要 CV，超出现栈 |
| 图表库（ECharts 等） | 一期用 LLM 文字周报，够用 |
| 热量精确计算 | 记录成本高、"效果"期再议 |
| 混合检索 / 评估 / 队列 / RBAC | 同 interview-rag 的画线 |
| 系统"自动生成训练计划" | 属于 agent 二期的任务，一期只问答已有资料 |

## 7. 分期

| 阶段 | 内容 |
| --- | --- |
| 一期（本次） | 三条主线 + 五条验收全通的闭环 |
| 二期（可选） | 周报图表、热量/体脂统计、共享/家庭成员 |
| 三期（可选，agent 向） | 自动生成/调整训练计划、主动打卡提醒（LangGraph，届时再定） |
