# 03 · RAG 设计（简版）

> 目的：够用。先读懂"为什么这样够用"，再决定以后要不要加深。

## 0. 术语（扫盲）

| 术语 | 一句话 |
| --- | --- |
| Chunk（块） | 文档切分后的最小检索单元，一段约 500 字的文本 |
| Embedding（向量） | 文本 → 固定长度浮点数组，语义近则距离近 |
| 检索（Retrieval） | 用问题的向量找最相似的 topK 个块 |
| 增强（Augmented） | 把检索到的块拼进 Prompt，作为回答的依据 |
| 生成（Generation） | 大模型照资料作答，要求标注引用 |
| 幻觉 | 模型编造不存在的内容——RAG 的第一使命是压制它 |

## 1. 切分

使用 LangChain `RecursiveCharacterTextSplitter`：

```python
# 治分优先级：段落 > 句子 > 字符；先按大边界切，超长块再递归下钻
splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,          # 块大小（字符）
    chunk_overlap=80,        # 重叠，防关键句被切断
    separators=["\n\n", "\n", "。", "！", "？", "，", " ", ""]
)
```

每个块入 Chroma 时带 metadata：

| 字段 | 用途 |
| --- | --- |
| doc_id / doc_title | 引用溯源、按文档删除 |
| UserId | 数据隔离过滤 |
| seq | 块序号，保持引用顺序 |
| source | 来源页码/章节（loader 能拿到就填） |

**已知软肋（画线区）**：表格/跨页内容会碎、扫描件无文本——现状标注为解析失败原因即可。

## 2. 向量化

- 模型 `BAAI/bge-m3`（1024 维，中文强，硅基流动 API）
- 批量调用：多个块一次请求，省接口往返
- 换模型 = 向量空间全变：保留原件 + 提供「重新向量化处理」的重试入口（闭环的失败重来路径）

## 3. 检索

纯向量检索，简单可控：

```
问题 → embed → chroma.collection.query(
    query_embeddings=[q_vec],
    n_results=5,
    where={"user_id": 当前用户}
)
```

- 结果按相似度排序，取 topK=5 进 Prompt
- **为什么不做混合检索**：闭环业务先跑通，BM25 通道是"召回率实验告诉我们不够用了"之后的二期动作（不提前为不会发生的问题设计）

## 4. Prompt（防幻觉的闸门）

```
你是健身教练助手。严格依据下面的【资料】和【我的数据】回答，规则：
1. 计划/饮食类问题只能使用资料中的信息，禁止编造；
2. 引用资料的句子末尾标注编号，如 [1]；
3. 效果类问题必须用【我的数据】里的数字，没有数据就直说"记录不足，无法判断"，不得推测；
4. 资料不足以回答时，直接回复"知识库中没有相关内容"。

【资料】
[1] 《腿部训练计划》（章节：深蹲日安排）
<chunk1 原文>
[2] 《减脂营养指南》（章节：晚餐安排）
<chunk2 原文>

【我的数据】
近一周：训练总容量 12000kg，体重 72.3kg（-0.6kg），记录 4 天

【用户问题】
<question>
```

要点：系统提示里的**三条规则**是抑制幻觉的关键，比任何"高级技巧"都重要。

## 5. 引用溯源（本项目与'调 API'项目的分水岭）

- LLM 流式输出里的 `[1]` 由后端映射到 metadata（标题/章节/原文）
- SSE 首个事件推送 citations，前端在回答下方渲染引用卡片，点击展开原文
- **可验证的回答才可信**——这是 RAG 产品区别于普通聊天机器人的核心体验

## 6. 会话与多轮（一期最简）

- 每轮检索前，把当前问题 + 上一条问题**拼接**（若当前问题是"它怎么实现的？"这种指代词，
  全部交给模型在 Prompt 里自行理解；不做过度的指代消解）
- 会话记录落库，历史可回看

## 7. 诚实的边界（简历上不写、面试可讲）

- 检索质量未做系统评估（二期加评估集与命中率指标）
- 中文表格/扫描件解析效果有限
- 纯向量检索对"专有名词精确匹配"较弱（这正是混合检索二期的动机）
