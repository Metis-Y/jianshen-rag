# 04 · 数据与接口设计

## 1. SQLite 表结构（SQLAlchemy 模型）

```python
class User(Base):
    id: int pk
    username: str unique
    password_hash: str              # bcrypt
    created_at

class Document(Base):               # 训练计划/营养资料等
    id: int pk
    user_id: int fk
    filename: str
    file_md5: str                   # 秒传 + 幂等
    size_bytes: int
    category: str                   # plan / diet / other（可选分类，便于检索过滤）
    status: str                     # PENDING / PROCESSING / READY / FAILED
    fail_reason: str nullable
    chunk_count: int
    created_at / updated_at

class WorkoutLog(Base):             # 效果主线：一次训练记录
    id: int pk
    user_id: int fk
    date: date
    exercises: JSON                 # [{"name":"深蹲","weight":80,"sets":5,"reps":5}, ...]
                                    # 快速模式允许只记 name（重量/组数/次数可缺省，不参与容量计算）
    note: str nullable              # 感受
    created_at

class BodyMetric(Base):             # 体重/体脂等
    id: int pk
    user_id: int fk
    date: date
    weight: float nullable
    body_fat: float nullable        # 预留，一期不参与统计
    sleep_hours: float nullable     # 预留（二期恢复线用）
    soreness: int nullable          # 预留：1~5 酸痛度（二期恢复线用）
    created_at

class DietLog(Base):                # 饮食主线：轻量记录
    id: int pk
    user_id: int fk
    date: date
    content: str                    # 吃了什么
    avoid: JSON nullable            # 该次备注的忌口/标签（如 ["牛奶"]）
    created_at

class Preference(Base):              # 用户档案：长期忌口、目标
    id / user_id unique
    goal: str nullable              # 减脂/增肌/维持
    allergies: JSON nullable        # 长期忌口，如 ["牛奶","花生"]
    updated_at

class Conversation / Message / Feedback  # 同 interview-rag
```

**设计要点**：

- 训练日志用**单条 JSON** 存动作列表，不做 exercise/exercise_set 零散表——够算"总容量"
  `Σ weight×reps×sets`，又避免过度建模
- 长期忌口放 `Preference`（一次设置），当日记录里的 `avoid` 属于临场补充

## 2. Chroma 组织（同 interview-rag）

单 collection `kb_main`，metadata 含 `doc_id / doc_title / owner_id / seq / source`，
`category`（plan/diet）便于按主题过滤。私有检索 `where={"owner_id": me}`；
未来共享检索 `$or`（我的 ∪ 共享给我的）。

## 3. API 定义（前缀 /api，凡数据操作均校验 user_id）

### 认证

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | /auth/register | {username, password} |
| POST | /auth/login | → {token} |
| GET | /auth/me | 当前用户 + 目标/忌口 |

### 资料（计划/营养文档）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | /documents | multipart（含 category），同步处理 |
| GET | /documents | 列表（可按 category 过滤） |
| POST | /documents/{id}/retry | FAILED 重处理 |
| DELETE | /documents/{id} | 磁盘 + Chroma + 记录三处同步删 |

### 记录（效果/饮食）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | /workouts | 训练日志 {date, exercises[], note} |
| GET | /workouts?from=&to= | 区间训练记录 |
| POST | /metrics | 体重 {date, weight} |
| GET | /metrics?from=&to= | 体重序列 |
| POST | /diets | 饮食 {date, content, avoid[]} |
| GET | /diets | 区间饮食 |
| PUT | /preference | {goal, allergies[]} |

### 问答（SSE，POST /api/chat）

```json
{ "question": "我最近一周深蹲进步了吗？", "conversationId": 1, "documentIds": [1] }
```

事件协议：`citations → message(delta) → done/error`（同前）。效果类问题由后端先聚合
SQLite 区间数据，作为结构化上下文拼进 Prompt，与检索结果一起交给 LLM。

### 会话与反馈 / 统计

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET/POST | /conversations、/conversations/{id}/messages | 同前 |
| POST | /messages/{id}/feedback | {positive: bool} |
| GET | /stats | 资料数 / 记录天数 / 问答数 / 好评率 + 最近体重与总容量 |

## 4. 效果主线的实现路径（关键）

用户问"这周趋势"时，后端**不依赖 LLM 猜数据**，而是：

1. SQLite 聚合：区间训练总容量、体重首末值、变化量、记录天数
2. 把这组小数字（如"总容量 12000kg，体重 -0.6kg，记录 4 天"）作为结构化事实块
3. 与 RAG 检索到的资料块一起拼 Prompt，要求 LLM 用数据说话、不编造

这一步是"效果主线"可信的关键：**数字来自 SQL，语言组织交给 LLM**。
