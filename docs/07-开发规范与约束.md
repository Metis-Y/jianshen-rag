# 07 · 开发规范与约束

> 项目虽小，规范不松。以下约束是「设计文档 → 代码」这条线的纪律。

## 1. 接口契约（硬约束）

- 所有 JSON 响应统一包络：`{ "code": 1, "message": "ok", "data": ... }`，
  **code=1 为成功**，错误码见 `docs/05` 错误码表
- 接口字段与 `docs/05-接口文档.md` 完全一致；改接口 = 先改 05，再改代码
- 数据隔离（安全底线）：**任何查询必须按当前用户过滤**——
  SQLite 查询带 `user_id`、Chroma 检索带 `where={"owner_id": user_id}`；
  访问他人资源返回 `code=40301`，而不是悄悄漏数据
- SSE 事件协议固定四种，不加新事件名

## 2. Python 代码规范

- PEP 8 + **类型标注**（FastAPI 项目类型标注=免费文档）
- 分层按 `docs/02` 目录结构，模块职责单一：
  - 路由不写业务逻辑（校验 + 调 service + 包 envelope）
  - 数据访问集中在 db/models 与 repository 函数，路由不裸写 SQL
- LLM / Embedding 调用统一走一个 client 模块，`base-url/api-key/model` 全走配置
- 密钥/ token 不落日志；生产/演示前把 key 从代码里清干净

## 3. 依赖纪律

- 只用 `docs/02` 选定的组件；**要新增依赖，先改 docs/02 的选型记录，再 pip install**（记录“为什么加”）
- 版本锁定用 `requirements.txt`（`pip freeze` 前人工裁剪，只留直接依赖 + 备注）

## 4. Git 规范

- Conventional Commits，中文描述，沿用之前项目风格：
  `feat(chat): ...` / `docs: ...` / `fix: ...` / `test: ...` / `chore: ...`
- **每完成一个验收点一个 commit**（对照 docs/06 里程碑），不攒大提交
- 分支策略：`main` 保持可运行；新主线/实验开 `feat/*` 分支，验收通过后合并

## 5. 错误处理纪律

- 所有异常在全局处理器统一转 envelope；**对外 message 说到人话**
  （如"文档解析失败：疑似扫描件"），堆栈只进日志
- 外键/约束类异常不可直接透传给前端，映射为对应错误码

## 6. 验收纪律

- 每个接口必须有 curl 可复现的成功/失败示例（写进 docs/06 验收备注或 tests/）
- 对照 `docs/01` 五条验收标准，每天收盘自检；测试数据用独立账号，不污染演示账号

## 7. 演示前检查清单（D6 用）

- [ ] .env 存在且被 gitignore；GitHub 上无历史提交泄露真实 key
- [ ] 默认账号密码在 README 中说明
- [ ] 上传一份示例资料跑通五条验收标准
- [ ] 接口文档（docs/05）与实现 diff 为零
